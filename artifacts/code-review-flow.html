Code Review 流程导图

code-review 做的是对抗式审查：在用户划定的范围内穷尽覆盖，用 Unit Ledger 记账，再用门控与透镜决定方向与发现，最后按严重度升级成 findings。它不写代码、不改仓库——只交付可核对的审查结果。

触发 plan / spec / diff / 实现形态 / 对齐审计 近邻 写计划用 code-plan，不走本 skill 硬约束 AGENTS.md · CONTRIBUTING · ADR

一句话定调

固定原始目标，挑战实现路线。优先找：减层（透传包装、一次性抽象）、减复杂度（code-judo：能删分支/模式/助手就删，不是挪地方）、增可靠（正确性、契约、状态、并发、迁移风险）。

核心不变量

Coverage 决定查什么；Ledger 记录每条结论；Bar 只决定哪些升级成 narrative finding。 风险权重可以调整审查顺序与深度，但绝不能决定某个 unit 是否进入清单、也不能降低阅读底线。

审查对象

  • 代码计划草稿、规格、迁移设计
  • diff / 实现形态
  • 与权威源的对齐 / 完整性审计
  • 「这个方向对不对」类判断请求

明确不做

  • 抽样式「挑重点看」
  • 用自信度代替严重度过滤
  • 无单独授权的编辑 / commit / push
  • 把计划写作当成审查（那是 code-plan）

主流程：从范围到交付

流程是序列；并行只发生在「单元过多 / 风险集中」时的透镜 fan-out。每一步的产物都要能回到 ledger。

01

定范围

用户给出 diff、文件集、计划、或要对齐的权威源。范围由用户圈定；范围内覆盖必须穷尽，不得抽样。

输入
02

机械枚举 units

从源材料推导清单：diff hunk 列表、文件列表、render/AST 树——禁止从「我觉得重要」的心智模型出发。说清枚举依据，使账本可核对。

unit = 可独立偏离或失败的最小元素
03

打开 Unit Ledger

枚举完成的瞬间就建账：每行 ID + Subject + Locator，Verdict 先空。约 30 行以上或有委托时，落盘为 Markdown/CSV/JSON（临时目录、仓外），且永不删除。

Unit Ledger
04

审查（透镜 + 可选委托）

多数审查就地套透镜。单元过多或风险集中（多文件、公有 API/CLI/schema/迁移/持久化）时，按透镜派 read-only 子代理，按 ledger 切片，禁止采样。finder 只负责覆盖，不过滤。

DesignContractTestFit
05

门控（仅 plan/spec 等）

方向是否正确、高价值意图是否被误砍，由两道门负责——验收标准与测试清单不能替代方向判断。

Plan-DirectionHigh-Potential Preservation
06

归因 + 写回 ledger

对比 base：[NEW] vs [PRE-EXISTING]。替换/删除代码时，还要核对旧面强制的 guards/preconditions 是否存活。关闭 unit = 读完其全部行 + 写入明确 Verdict。

Verdict · Evidence
07

Bar 过滤 + 可选 synthesis critic

Bar 只决定叙事升级，不决定是否审查。高风险或证据冲突时派 synthesis critic：挑战草稿 findings，不生产新候选。

blocker · raise · nit
08

交付并过停机条件

Coverage 账本（完整 ledger）→ Findings → Open questions → 总判断。任何未关闭范围必须以 ID + Subject + Locator 点名，禁止把部分覆盖说成完整。

Stop Rules

Unit Ledger：覆盖的账本

Ledger 不是报告装饰，而是覆盖声明的唯一载体。「已审查」是观察主张：只有「枚举了 N、关闭了 N」且账本可核对时才成立。

每一行必有字段

字段 含义 约束
ID 本审查内唯一且稳定的 join key 禁止事后改号；裸 ID / 区间 / 文件标签不能代替覆盖主张
Subject 这个 unit 是什么 具体到能与其他 unit 区分
Locator 可独立使用的指针 文件+符号/行、diff hunk、文档节、AST 路径、源/目标对等
Verdict 关闭时的结论 correct/aligned · authorized divergence · defect · unreviewed（命名 blocker）
Evidence 证据或 blocker 缺证据 → 标 unreviewed，审查 partial

必须成立的等式

enumerated units = ledger rows = unique IDs = reviewed + explicitly-unreviewed

Identifier integrity（标识完整性）

下列任一即 broken ID：

  • duplicate — 两行共用同一 ID
  • orphan — 结果引用了不存在的行
  • undefined — 行缺 Subject 或 Locator
  • unresolved — 引用映射到 0 行或多于 1 行
  • renumbered — 枚举后改了 ID

有文件账本时，这些检查必须对文件机械执行（数行、数唯一 ID、列空 verdict），禁止凭记忆断言。

委托时的身份所有权

枚举者拥有 identity：任务包携带完整行（ID + Subject + Locator）与 Slice/owner；审查者用同一批 ID回写；只有枚举者可追加新行并更新总数，既有行永不改号。反驳或撤回的 finding 保留行与 ID，就地改 verdict 并注明原因。

什么算一个 unit

Diff / 代码

每个变更 hunk + 它所触及的契约面。替换/删除代码时，旧 guards 与 preconditions 也要进枚举。

对齐 / 奇偶审计

每个 render 节点、条件分支、handler、请求/载荷、状态写入、资产、文案与样式元素；缺侧也要显式标记。

两道门：方向与高价值保留

只在审查计划 / 规格 / 拟定实现路径 / 迁移设计，或被问「方向对不对、值不值得做」时激活。验收、测试、排期、措辞不能顶替门控证据。

Plan-Direction Gate

在评价「计划质量」之前必须齐备：

  • 目标结果与显式约束
  • 计划试图保住的最高价值意图
  • 策略与归属点（数据源、状态写、共享契约、调用边界…）
  • 问题 → 根因/决策点 → 改动 → 预期效果的逻辑链
  • 同目标下的可信替代（更早修复点、更小范围、删层）
  • 有界最优判断：best-supported / adequate / wrong / unjudged

缺证据就标 unjudged 并写开放问题；可接受的妥协须写清牺牲的不变量、接受的风险、依赖约束与停止条件。

High-Potential Preservation Gate

准备建议砍掉、推迟或降级某个组件前，先分类：

  • Unnecessary scope — 非所求、投机、重复所有权 → 可砍/ defer
  • Under-specified core — 可能是高价值核心但边界不清 → 保意图，要求澄清/去风险
  • Risky unauthorized boundary — 改公有行为/契约/持久化等未授权 → 暂停或问授权

方向级砍减 finding 必填：Classification · Evidence · Preserved outcome · Lost outcome · Preservation path · Smallest correction。「更简单」 alone 不够。

禁止的塌缩

不得用「更小/更清晰/更少风险」静默压低计划天花板。若高价值结果依赖未决的意图边界，停在边界问题、假设检验或 learning slice，交给用户决策——而不是替用户缩小野心。

透镜：查什么、谁过滤

透镜描述审查角度；需要 fan-out 时，透镜文案就是子代理 prompt。 Finder 的职责是覆盖，不是过滤——不确定与低严重度候选也要带回，带 confidence 与预估 severity；对照 Bar 的过滤发生在主审与 synthesis critic。

Design shape

浅接口、信息泄漏、战术补丁（只加分支/模式/回退不减根复杂度）、弱所有权、应被设计消掉的错误处理、纯转发层。设计发现必须用 APOSD 词汇：读者任务 + 症状（change amplification / cognitive load / unknown-unknown）+ 原因（dependency / obscurity）。拒绝无此映射的「cleaner / more DRY / 加注释」。

Contract surface

公有/共享契约：API、CLI、schema、持久状态、生成物、包装层、迁移。新能力承诺、静默改写/归一化、重新解释上游契约、派生身份碰撞、未文档化的行为变化、迁移丢掉源基线、动作仍在但 gating 谓词消失。

Test validation

回归证据：可能无覆盖就回归的行为；测私有状态/调用顺序/组件名而非公有行为；该真用却被 mock；仅为可测性开的生产缝；只证明新路径、不保护既有行为的计划。未触及代码的覆盖缺口不报。

Implementation fit

与本地代码库是否合身：重复现有 owner 的 helper、一次性抽象、错误层逻辑、近复制变体、为未来灵活性开的选项/分支、调用不存在或被绕过的 helper。除非是最小修正，不提议邻接重构。

Synthesis critic（不同角色）

高风险或证据冲突时派出。不生产新候选，只挑战草稿：证据是否真实、归因是否对 base 正确、是否清过 Bar、APOSD 是否完整、子代理严重候选是否被静默丢掉、覆盖账是否闭合、枚举是否从源材料独立重导并 diff、ledger 是否通过 identifier-integrity、反驳是否就地改 verdict 而非静默删除、aligned 行是否被抽查而非盲目采信。 每条挑战返回：target · issue · evidence · action（keep / drop / retag / reword / reorder / verify / surface）。

Bar：什么进入 findings

每个 unit 的 verdict 都在 ledger 里；Bar 只决定哪些已关闭 unit 升级为叙事 finding。 升级底线：可能造成错误行为、破坏契约、损坏或不一致状态、测试失败、或误导结果的问题。低于此线且不影响合并决策/后续计划的观察，可以只留在 ledger。

严重度 含义 排序
blocker 正确性 / 契约 / 状态类问题 最先
raise 真实问题，可接受后续跟进 中
nit 小抛光 最后

过滤纪律

按严重度与合并相关性过滤，不按自信度过滤。对合理但不确定的正确性/契约/状态问题：标出不确定性与如何确认，而不是静默丢弃。不要为了「finding 少一点」压制真的低严重度问题——按真实严重度报告并排在后面。

归因规则（diff 有 base 时）

  • NEW — 本次引入，或被本次显著恶化
  • PRE-EXISTING — 基线上已成立；仅当触及同一表面且阻塞意图、被恶化、或用户要求更广审计时才报告
  • 不确定就直说，不要默认 NEW
  • 对齐审计无 base 时，用 per-unit 结论（aligned / authorized divergence / defect），不强贴 NEW/PRE-EXISTING

输出契约与停机条件

散文用用户主语言；代码符号、路径、错误信息保持原文。无单独授权时：不编辑、不 commit、不 push。

交付顺序

  1. Coverage 账本 枚举依据；enumerated / reviewed / unreviewed 计数；完整 Unit Ledger（内联、附录或绝对路径链接）；identifier-integrity 例外；未覆盖行用 ID + Subject + Locator
  2. Findings 每条引用 ID + Subject + Locator，带严重度与 [NEW]/[PRE-EXISTING]（或对齐审计的 per-unit 结论）。plan/spec 时方向/前提/归属/逻辑链问题排在同等或更低严重度的验收/测试 finding 之前
  3. Open questions 会实质性改变决策的问题
  4. Overall judgment 短结论；点名 blocked/unreviewed 面。plan 方向 verdict：best-supported / adequate but suboptimal / wrong/unsupported / unjudged；高价值版合理但欠规格时写 under-specified，默认不要压成更小计划

Finish 前必须勾完

完整 Unit Ledger 已包含或可链接；Subject / Locator / Verdict 可从报告追溯 任何审查
Identifier-integrity 通过（有文件则机械检查）；ledger 文件未删除 任何审查
覆盖账闭合；归因、严重度、残余风险清晰 diff / 代码审查
替换/删除代码时：guard / precondition 存活检查已做 Attribution
Plan-Direction 有明确 verdict；每个重大砍/defer/narrow 满足 High-Potential Preservation；开放问题已点名；验收/测试观察未挤掉更重要的方向判断 plan / spec

无法关闭时怎么结束

点名未覆盖或未交付集合为 ID + Subject + Locator，并写清关闭所需条件——永远不要把部分覆盖呈现为完整。验证不可用或越界时，写明使用的次优证据。
