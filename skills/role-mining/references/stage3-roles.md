# Stage 3 — 角色推断规程

输入：`signals/`＋`signals-manifest.md`＋`census/census.md`＋`signals/_open-schema/` 对照结论。
输出：`roles.md`（最终交付物）。

## 3A. 决策与摩擦模式提取

从信号中先归纳四张清单（每条挂 ≥1 个 session 证据）：

1. **必须亲自拍板的决策类型**（含语料中的典型形态）
2. **最消耗判断力 / 易烦躁的问题**（怒点）
3. **对 agent 的高频纠正方向**（要 / 不要 / 相对放过——「相对放过」必须同时引用 census.md 的放权证据，不能只来自高摩擦会话内部）
4. **稳定相位切换**（会话内反复出现的阶段序列与切换硬信号）

## 3B. 聚类为角色（4–7 个）

- 角色 = **反复出现的判断职能**，不是 pipeline 工位名，也不是某仓库/工具的专名。
- 每个角色定义：核心职责 / 典型触发 / 主动吸收 / 升级给人 / 成功标准 / ≥2 个语料示例（session + 原话）。
- **Owner（用户本人）永远在系统外**：不可逆偏好、参照冲突、范围、公开形态、收口令归人，不做成 agent。
- **相位类型标注（必做）**：每个角色标 `批处理型` 或 `对话型`。
  - 批处理型：目标是压缩 Owner 轮次（决策包一页批完、清单内做满）。
  - 对话型：目标不是减少轮次，而是提高每轮质量——能被连环质询、能出 demo、前后话术自洽、复杂度可叫停。设计/塑形类职能在真实语料中几乎总是对话型；把它写成「一次通过出方案」会在落地时立刻失真。

## 3C. 残差记账（必做，不许跳过）

聚类完成后，逐条过一遍**全部高价值信号**：每个会话要么映射到 ≥1 个角色（写进角色示例或触发），要么进 `roles.md` 的「残差清单」一节：

```markdown
## 残差清单（高价值但未入桶）
| Session | 涉及的判断轴 | 为什么现有角色装不下 | 处置 |
```

- 同一判断轴上残差 ≥3 个 session → 该轴是**候选新角色**，必须显式决定：新增角色 / 扩展某角色定义 / 记录为域外并说明理由。
- 开放模式对照（stage2 §2B）发现的分歧轴同样入表。
- 描述性结论静默丢弃不合形的高价值样本 = 保真缺陷。残差清单就是防这个的。

## 3D. 双层输出结构

`roles.md` 分两部分，两层共存、互不覆盖：

- **Part 1（描述性）**：只看本语料的原始角色，允许耦合于语料主场景，命名贴语料工位。含 3A 四张清单、角色定义、默认协作顺序、决策人格小结、残差清单。
- **Part 2（规范性）**：跨域提炼的通用角色。含提炼原则表（每条原则注明对原始角色做了什么操作）、通用角色定义、原始→通用映射表（含「提炼时丢掉的外壳」列）、通用协作顺序与最小编排、可粘贴 prompt 骨架。
- 命名原则：短词平行、相位自明、领域中立（不出现具体仓库/流程专名）;通用角色必须能指回原始角色（一对多可追溯）。
- 合并两个原始角色时必须写合并依据（通常是「升级给人的问题类型相同」），并注明可再拆的子模式。
- 明确写出证据层级：L0 cleaned 原话 → L1 信号摘录 → L2–3 归纳 → L4 Part 1 聚类 → L5 Part 2 提炼与命名（L5 含 Owner 拍板，不是纯数据观测——不要把 Part 2 说成「数据证明恰好 N 个角色」）。

## 3E. 覆盖与局限声明

`roles.md` 末尾如实写：读了什么、没读什么（如未全量精读 cleaned）、价值/干预标签是启发式、开放模式对照的收敛程度、残差处置情况。**未检验的范围要点名，不许用完成度语气盖过去。**

写完后进入 Stage 4 回放验证（`references/stage4-replay.md`）——角色定义在被回放检验之前只是分类学，不是被验证的设计。
